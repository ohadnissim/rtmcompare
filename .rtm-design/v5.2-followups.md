# RTMcompare v5.2 — Follow-up Build List

*Generated 2026-05-13. The v5.2 visual upgrade shipped (commits `a29de5c` → `d7c2403`). Every UI surface is wired and reachable. This document lists the **product features behind those surfaces** that still need real implementation, plus minor polish gaps.*

Complexity legend: **S** = ≤1h surgical · **M** = ½–1d focused work · **L** = multi-day product feature.
Priority: **P0** = blocks ship · **P1** = next-release · **P2** = nice-to-have.

## A. Real product features (the surfaces are containers waiting on data)

### A1. Teacher dashboard submission pipeline — **L · P1**

**The gap.** `TeacherDashboard.tsx` renders an empty state today because `submissions={[]}` is hardcoded in `App.tsx` line ~1009 (where `<LearnCenter />` mounts). No submission pipeline exists in the codebase.

**To build.**
- A schema for `StudentSubmission` (already typed in `TeacherDashboard.tsx`; treat that as canonical).
- A storage backend — local-first (SQLite via Python daemon) or cloud — for student uploads tagged with `studentId`, `assignmentId`, `courseId`.
- A submission flow on the student side: when a student in Learn mode runs an analysis, the result + verdict gets posted to the teacher's queue.
- An assignment-creation flow on the teacher side (course name, brief text, rubric thresholds).
- Wire `TeacherDashboard.submissions` to the real list, sorted newest-first.

**Acceptance.** A teacher opens RTMcompare in `learn` mode + `teacher` role. The roster shows real students with their last submission verdict + status dots. Clicking a row opens the submission's analysis. Clicking "EXPORT GRADEBOOK" produces a multi-page PDF.

**Files.** `src/components/v52/TeacherDashboard.tsx`, new `src/lib/submissions.ts`, possibly Python daemon endpoints.

### A2. Drill engine for LearnHome — **L · P1**

**The gap.** `LearnHome.tsx` renders 6 hardcoded seed drill cards. Each `onStart` is `console.log('start drill', title)`. No drill UI, no scoring, no history persistence.

**To build.**
- A drill engine: present an audio prompt, capture user input, score against a target, persist the attempt.
- At minimum the 6 seed drill types should be implemented:
  1. **LUFS guessing** — play a clip, user guesses LUFS-I within a tolerance.
  2. **Stereo image** — play a clip in M/S/L/R/stereo, user identifies the channel.
  3. **Masking detection** — present a 2-track mix with a masking collision; user identifies the offending band.
  4. **True peak / clip detection** — does this clip distort on lossy playback?
  5. **Genre loudness profile** — match a LUFS distribution to a genre.
  6. **Mix critique balance** — play a master with one element mis-balanced; user identifies which.
- Drill-attempt persistence: write to local store keyed by `studentId × drillId × timestamp` with the score.
- LearnHome should read history and recompute `attemptCount` / `recentScores` / `cumulativeGrade` per card.
- "Save practice report" should pull the actual last-attempt data, not seed values.

**Acceptance.** Click "Start drill →" on a card → drill UI takes over → user completes attempt → score saved → return to LearnHome → that card's sparkline + grade reflect the new attempt.

**Files.** New `src/components/v52/drills/` directory with one component per drill type, `src/lib/drillStore.ts`, modifications to `LearnHome.tsx` to read live data.

### A3. ReleaseReadiness real export trigger — **M · P0**

**The gap.** `ReleaseReadiness.tsx` calls `onMasterForRelease()` which is a `console.log` stub. The gold "Master for release" CTA needs to actually trigger an export.

**To build.**
- Wire `onMasterForRelease` to the existing export pipeline (likely `ExportButton.tsx` or `EQExportButton.tsx` handlers) with platform-specific target params (LUFS / peak / sample rate per platform).
- Optionally: produce one bounce per platform instead of one master (Spotify -14 LUFS, Apple -16 LUFS variants). Or stick to a single master.
- Release-card PDF print is already wired in parallel — the CTA fires both the export and the print.

**Acceptance.** Click "Master for release" → existing export pipeline runs with producer-mode target spec → result file appears + release card prints.

**Files.** `src/components/v52/ReleaseReadiness.tsx`, `src/App.tsx` to wire the prop, possibly `src/components/ExportButton.tsx` to accept platform-target overrides.

### A4. CertificateID + sha256 persistence — **S · P1**

**The gap.** `printProCertificate` generates a fresh 8-char cert ID and 12-char sha each time. There's no record of issued certificates anywhere.

**To build.**
- A local log of issued certificates (date, track, engineer, cert ID, sha, verdict). One row per print.
- Eventually a verify path: an issued cert can be re-checked against the original audio.
- Stretch: a public sha-anchor (Sigstore Rekor, TSA, or simply a signed JWT) — but that's enterprise scope; document the rule, don't implement.

**Acceptance.** After issuing a cert, the local DB has a row. A "Recent certificates" view (probably in Settings or a new surface) shows past issuances.

**Files.** `src/lib/certificate.ts` (extend to persist), new `src/lib/certificateLog.ts`.

### A5. Annotation authoring tool for teachers — **M · P2**

**The gap.** `public/v5.2-annotations.json` holds 9 seed annotations. Teachers extend by editing the JSON manually. There's no in-app authoring UI.

**To build.**
- Inside `TeacherDashboard`, an "ANNOTATIONS" tab or sub-route.
- A form: pick a metric (LUFS-I / dBTP / LRA / PLR / stereo_correlation), pick a context (`a_louder`/`b_louder`/etc.), set delta threshold, write the body.
- Save → appends to a local annotations file (or remote, if multi-teacher).
- Body editor: rich-text or markdown with live preview. Body length 50-200 words target.

**Acceptance.** A teacher writes an annotation in the UI, saves, then a student running an analysis with that delta sees the annotation in the side panel.

**Files.** New `src/components/v52/AnnotationEditor.tsx`, modifications to `TeacherDashboard.tsx` to expose it.

## B. Small wiring tasks (1-3 hours each)

### B1. File duration on cover — **S · P2**

**The gap.** When a file is dropped, `CoverSurface` shows `WAV` (format from extension) but no duration. Falls back to em-dash.

**To build.**
- On drop, decode just enough of the audio header to extract duration. WAV/AIFF headers contain duration directly; MP3/FLAC need a quick frame scan.
- A tiny helper `getAudioDuration(filePath): Promise<string | null>` that returns `"3:42"` formatted.
- Pass duration through `CoverWiredEmptyState` → `EmptyStateV2` → `CoverSurface`.

**Acceptance.** Drop a 3:42 WAV → cover shows `WAV · 3:42` under the filename.

**Files.** New `src/lib/audioDuration.ts` (or extend `python-bridge.ts` to call the daemon — daemon already opens these files for analysis). `src/App.tsx` `CoverWiredEmptyState` to compute and pass.

### B2. `stereo_correlation` annotation wiring — **S · P2**

**To build.**

**Acceptance.** In student/teacher mode, click the stereo correlation Δ in PhaseCorrelation → annotation panel opens.

**Files.** `src/components/PhaseCorrelation.tsx` only.

### B3. ThemedConfirmDialog component — **M · P1**

**The gap.** The gold-budget spec (`v5.2-gold-budget.md`) prescribes that confirm dialogs with `tone='final'` or `tone='destructive'` should render a gold confirm button. The component doesn't exist in this codebase.

**To build.**
- A reusable `ThemedConfirmDialog` matching the v5.2 aesthetic: ink modal, 2px corners, Instrument Serif italic title, tracked-caps eyebrow, audience-aware confirm-button copy.
- Props: `title`, `body`, `tone: 'default' | 'final' | 'destructive'`, `confirmLabel`, `onConfirm`, `onCancel`, `actionSlot?`.
- Gold for `final`/`destructive`, sand-ghost for `default`.
- Accessibility: role=dialog, focus trap, Escape cancels, prior focus restored.
- Replace `window.confirm()` calls across the app (audit log: there are a few — grep them).

**Acceptance.** Any destructive action (delete profile, clear history, etc.) prompts through ThemedConfirmDialog instead of native `window.confirm`. The gold CTA carries the commitment weight.

**Files.** New `src/components/v52/ThemedConfirmDialog.tsx`, replace native confirm() call sites.

### B4. Certificate Electron IPC PDF path — **S · P2**

**The gap.** `src/lib/certificate.ts` checks for `window.electronAPI?.exportCertificate` and falls through silently. Today it falls back to `window.print()` which is fine for browser/print-preview but doesn't produce a saved PDF file unless the user picks "Save as PDF" in the print dialog.

**To build.**
- An Electron main-process handler that accepts the certificate HTML/component output, renders it via `webContents.printToPDF`, and saves to a user-chosen location.
- Expose via `preload.ts` as `electronAPI.exportCertificate(html, filename)`.
- Certificate.ts will pick this up automatically (the detection code is already there).

**Acceptance.** "Generate certificate" → produces a saved `.pdf` file in `~/Downloads/` (or user-chosen folder) without going through the print dialog.

**Files.** `electron/main.ts`, `electron/preload.ts`, `src/lib/certificate.ts` (already detects — no change).

### B5. Audience picker — clear override path — **S · P2**

**Files.** `src/components/v52/CoverSurface.tsx`.

## C. Minor polish / known issues

### C1. `electronAPI.getPathForFile` compatibility — **S · P2**

The cover's `onDropA`/`onDropB` use `(window as any).electronAPI?.getPathForFile?.(file)` (mirroring `FileDropZone.tsx:43`). On Electron 32+, `File.path` is deprecated and `webUtils.getPathForFile` must be used. Verify the preload bridge exposes this correctly across all supported Electron versions.

**Files.** `electron/preload.ts`.

### C2. Recent-entry `id` collision — **S · P2**

`CoverSurface` recents use `entry.path ?? entry.name` as the `id`. If two history entries share the same name (different paths), or the same path (rare), the click resolution is ambiguous. Generate stable IDs (sha of path+ts) instead.

**Files.** `src/App.tsx` `CoverWiredEmptyState`, possibly `src/types.ts` if HistoryEntry gets an `id` field.

### C3. Light-mode end-to-end coverage — **M · P1**

The paranoia design pass tokenized hex literals across 86 files, but light-mode (`[data-theme="light"]`) was never walked end-to-end with every surface visible. Run a full surface tour in light mode; flag any remaining hardcoded hex.

**Files.** Project-wide grep for `#[0-9a-f]{6}` in `style={{`, then convert.

### C4. TabBar overflow at 12+ tabs — **M · P2**

Audit flagged this. TabBar has `overflow-x-auto` but no overflow menu / dropdown at high tab counts. Add a "+N more" overflow when tabs scroll horizontally.

**Files.** `src/shell/TabBar.tsx`.

### C5. `prefers-reduced-motion` coverage — **S · P2**

Only `SpectrogramView` honors it today. Walk components with animations/transitions — TrackRow `transition-all`, FlowChart-like elements — and gate behind a global `@media (prefers-reduced-motion: reduce)` CSS reset or Tailwind's `motion-safe:` prefix.

**Files.** `src/styles.css` (add the global reset block).

### C6. `--color-text-muted` collision audit — **S · P2**

A few non-audited files (RefOnlyTour, EngineerTipsPanel, EQExportButton, CommandPalette, CollapsibleSection, TranslationCheckPanel, ProfileDropdown) may still have `#7a7164` literals. Sweep them.

**Files.** Grep `#7a7164` and `#e05a5a` across `src/`; replace with tokens.

### C7. v5.2-preview.html dev launcher — **S · P0**

`public/v52-preview.html` is a dev-only launcher for testing audience flags. Vite copies `public/` into the build — this file would ship. Either:
- Delete before tag,
- Move to `dev-only/` and gitignore from production,
- Or guard with a build-time env check.

**Files.** `public/v52-preview.html`.

### C8. Cover empty-state copy — **S · P2**

When neither A nor B is loaded, the cover shows tracked-caps "DROP REFERENCE" / "DROP {YOUR FILE/MIX/TRACK/SUBMISSION}". Consider adding a one-line italic body under each empty slot explaining what to drop ("WAV, AIFF, MP3, FLAC up to 192 kHz / 32-bit") — currently shown only in the legacy upload screen.

**Files.** `src/components/v52/CoverSurface.tsx`.

## D. Out of scope for v5.2 (note for v5.3+)

These were considered during the design-director consultation but intentionally deferred:

- **Onboarding/teaching surface** for first-time producers explaining what each metric means (LUFS, dBTP, LRA). The legacy `OnboardingTour` covers high-level flow but not metric pedagogy. Could mount inside the producer ReleaseReadiness as a `?` tooltip per platform row.
- **Multi-track album sequencing analysis** — RTMcompare today is per-track. An album-level QC verdict (inter-track loudness consistency, transition flow) would mirror FLOW's purpose but stay in mastering scope.
- **Engineer profile sharing** — `ProfileDropdown` lets you load custom profiles; sharing one as a `.rtm-profile` artifact (with editorial chrome — small Console Didone card) is a v5.3 idea.
- **The Sample Pack** — a curated set of reference tracks per genre served from within the app, so students can drag a reference without hunting for files. Editorial gallery, browse by genre, drag to FILE A.
- **A real-time meter mode** — RTMcompare today is one-shot analysis. A "Live monitor" mode where the meters update against incoming DAW audio (via RTMsend) would change the product class.
